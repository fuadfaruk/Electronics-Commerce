# ElectroMart Completion Plan

## Goal

Complete a single-store commerce MVP, not just a storefront demo. Deliver a tested live catalog, COD checkout, customer accounts, private guest tracking/claims, and protected staff management while preserving the existing phone-first visual design.

Planning is based on read-only audits. No application files, databases, deployments, or dependencies were changed. Tests/builds were not run; runtime-version commands were denied by planning permissions.

## Agreed Scope

- Both frontend and backend may change; the historical frontend-only/backend-read-only README boundary no longer defines this milestone.
- COD only. Deduct available stock when an order is accepted. Restore it exactly once on staff cancellation before shipment.
- Fulfillment: Pending -> Confirmed -> Shipped -> Delivered; Pending/Confirmed may become Cancelled. Payment is independently Unpaid/Collected. Staff record Collected only after Delivered; it means customer cash received, not courier remittance.
- Guest checkout and email/password customer accounts, using backend-owned ASP.NET Core Identity. Verification and recovery use configurable SMTP, with a local mail inbox for development.
- Every checkout requires email and phone. Account checkout uses the verified account email. Guest orders can be explicitly claimed by a verified matching-email account using fresh one-time order-email proof; never link by email match alone.
- A protected dashboard for an operator-provisioned Admin manages categories, products, stock, orders, fulfillment, and collection. No public staff signup, invitation UI, or role-management UI.
- Categories are API-managed, not restricted to the existing eight. Product images are ordered externally hosted HTTPS URLs, not uploads.
- Retain MySQL using MySQL 8.4 LTS, the released Oracle EF10 provider, and aligned EF/Identity 10. Provider compatibility tests and licensing review are release gates.
- Current database data is disposable development data. There are no external API consumers, so replace obsolete contracts in both halves together without compatibility shims.

## Retained Assumptions

- Preserve existing light-theme, phone-first layout, URL filters, load-more interaction, documented whole-BDT pricing/display, VAT-inclusive prices, BDT 80 delivery, and free delivery at merchandise subtotal >= BDT 5,000. Delivery/precision questions were skipped; retain these documented rules as assumptions. Require whole-taka new sale/compare prices stored as exact decimals ending in .00; reject fractional imports rather than silently rounding. Paisa support and zone pricing are out of scope.
- Retain existing IIS/MonsterASP deployment direction. Hosting questions were skipped; actual host capabilities remain a release gate, not grounds to change platforms silently.
- Keep ElectroMart branding and clearly identified sample development data. Production branding, merchandise, support contacts, and legal/privacy content must be supplied by the operator rather than invented.
- Out of scope: online wallets/gateways, refunds/returns, courier settlement, variants, wishlist/reviews, dark mode, coupons, delivery zones, uploads, customer address books, email changes/account deletion, and customer self-service order editing/cancellation.
- No production database reset, live deployment, commit, push, secret rotation, or hosting/GitHub-account changes are authorized by this plan. Necessary mutating Git cleanup requires its own one-shot confirmation.

## Contract Sketch

Keep the existing `/api/v1` prefix, but coordinate changed DTOs across both halves; there are no external consumers to preserve. Browser mutations reach these through the same-origin BFF.

| Boundary | Proposed Contract |
| --- | --- |
| Catalog | `GET /Product` preserves `filters.ts` semantics: all q tokens, OR within comma/repeated category/brand sets, AND across criteria, inclusive min/max, stock=in, q-only facets. Add page/pageSize; return `{ items, totalCount, page, pageSize, facets }`. Sort keys: relevance, price-asc, price-desc, name-asc. |
| Product details | `GET /Product/by-slug/{slug}` and GUID lookup return dedicated detail DTOs, ordered images/specs/category metadata, sale eligibility, and bounded related summaries. Home collections are bounded separately, never inferred from page one. |
| Categories | `GET /Category` supplies dynamic navigation metadata/counts. Protected create/update/archive/delete and admin listing provide managed taxonomy with optimistic versions. |
| Quote | `POST /Checkout/quote` takes `{ items: [{ productId, quantity }] }`; returns owner-bound quote ID/15-minute expiry, current lines, BDT totals and availability problems. It reserves no stock; server-issued account/guest cookies determine owner. |
| Order acceptance | `POST /Order` takes `Idempotency-Key`, `{ quoteId, contact, deliveryAddress, notes? }`; returns a safe receipt. Account email/ownership are assigned server-side. |
| Account orders | Authenticated verified `/Account/orders` list/detail are scoped by subject, not body/query user IDs. |
| Guest tracking | Random per-order capability, hashed in storage, delivered in a URL fragment and exchanged through POST for an HttpOnly scoped grant; clear the fragment after exchange. Neither order GUID nor email is authorization. Original checkout-session replay is separately scoped. |
| Guest claims | Verified `/Account/order-claims` request/complete actions require matching immutable order email plus fresh, expiring, attempt-limited one-time email proof. Atomically claim an unowned order and revoke guest grants; never bulk-link by email. |
| Staff operations | Admin list/detail and versioned fulfillment/cancellation/collection actions; stock adjustments take `{ delta, expectedVersion, reason }` and an idempotency key. No generic entity/status or absolute stock overwrites. |

Affected boundaries: Core owns commerce entities/DTOs; Infrastructure owns Oracle EF, Identity storage, transactions and mail; API owns policies/controllers; frontend `src/lib` owns server-only transport/cart/catalog contracts and `src/app`/components own customer/admin UI. Tests and `.github/workflows` own validation/release artifacts. Retain the existing layered architecture; no extra service or identity database.

## Transaction Rules

- Money is server-owned decimal arithmetic on validated whole-taka prices. Snapshot unit price, quantity, line total, currency, subtotal, delivery, total and policy version; display exactly the confirmed amount, never a rounded client authority.
- Order lines snapshot product name/slug/price. Referenced products are archived rather than deleted. Structured contact/address snapshots do not change when an account or catalog entry changes.
- Quote ownership is immutable: verified account subject or unguessable durable anonymous session, never email or submitted user ID. Identity changes require a new quote only after any uncertain prior attempt has been resolved.
- In one InnoDB transaction, guard the owner/operation/idempotency key and accepted quote uniqueness, lock product IDs in consistent order, validate/reprice, conditionally decrement stock without going negative, insert the order/receipt/outbox, and commit. Test real-provider locking/row counts; bounded whole-transaction deadlock retries use the same attempt key.
- Same owner/key/payload retries recover the same order without a second deduction, including after a lost response or quote expiry. Different payload/key scope returns conflict. Retain order-linked keys/tombstones beyond response-cache expiry; never reinterpret an old unreplayable key as a new order. Recheck current ownership on replay, including after guest claims.
- Cancellation locks/version-checks the order first, permits only Pending/Confirmed, and atomically marks Cancelled/restores quantities once. Every checkout, cancellation and stock delta advances Product.Version; metadata updates exclude stock. Replays/stale writes cannot overwrite sales or repeat restoration. Commands have audit events and explicit version guards, with 409 for conflicts.
- Collection is a separate full-total Unpaid -> Collected action valid only on Delivered, with staff identity/timestamp. No inference from delivery, partial collection, reversal, refunds, or courier remittance accounting.
- Claim completion atomically checks account/email/proof/expiry/attempt count/unowned status, consumes proof, assigns the authenticated subject, and revokes guest capabilities. Claim/reset links and proof must be absent from logs, analytics, referrers, and public error details.
- Validation errors use 400; unauthenticated/expired account sessions 401; forbidden management 403; inaccessible order lookups avoid enumeration with 404; stock/price/stale-version/idempotency conflicts 409; expired quote/proof has an explicit safe expiry code; throttling 429; true temporary upstream/database outages 503. Do not label every database constraint failure as an outage.
