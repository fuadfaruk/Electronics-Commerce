# Private Telegram Order Notifications

Status: Implementation-ready plan. Planning only; no application source or non-plan documentation has been changed.

## Agreed Scope

- Use a Telegram bot rather than WhatsApp Business onboarding. The owner creates a bot with BotFather and starts a private chat; normal bot messaging requires no business verification or payment gateway.
- Customers use ordinary checkout and private order tracking. They need neither Telegram nor WhatsApp, see no messenger buttons/provider details, and never trigger browser-side bot requests.
- Automatically notify the owner's fixed private Telegram chat after each new order is saved. Include the order and contact details needed to contact the customer and manually confirm the order/payment arrangements.
- The user selected notification-only scope: retain existing order/payment bookkeeping, fulfillment rules and cash collection after delivery. No advance-payment/refund feature.
- Keep notification transport behind a backend-only boundary so it can be replaced later without changing customer requests or receipts. Implement Telegram only now, not a multi-provider framework.

## Existing Boundaries

- No online gateway or payment-method selector exists to comment out (`frontend/src/components/checkout/checkout-form.tsx:207-240`; `backend/src/ElectroApi.Core/DTOs/CommerceDtos.cs:67-71`). Replace COD-exclusive presentation with neutral manual-confirmation copy; do not comment out order/payment records or fabricate dormant gateway code.
- `CommerceRepository.AcceptOnce` atomically saves stock deductions, a `Pending` / `Unpaid` order, the idempotency receipt and protected customer email (`backend/src/ElectroApi.Infrastructure/Repositories/CommerceRepository.cs:55-103`). Exact replay returns the existing order before quote-expiry checks.
- Preserve checkout's accepted/recovered finish and purchased-quantity reconciliation (`frontend/src/components/checkout/checkout-form.tsx:88-95`), required email, identity/CSRF safeguards, guest capabilities and account tracking.
- Keep SMTP and its existing email-specific outbox (`backend/src/ElectroApi.Infrastructure/Mail/CommerceMail.cs`). It supports verification, password reset, guest access and order updates; never forward its capability-bearing customer email to Telegram.

## Implementation Tasks

1. Add an internal owner-order notification outbox to `backend/src/ElectroApi.Core/Entities/CheckoutRecords.cs` and configure it in `backend/src/ElectroApi.Infrastructure/Data/ApplicationDbContext.cs`. Use one unique row per order, an order FK, separately protected payload, creation/scheduling timestamps, current part index, attempt count, fenced lease identity/expiry, terminal timestamps, last provider message ID and a bounded safe failure code. Index pending work; add a forward EF/MySQL migration and snapshot update. Preserve original migrations and historical orders; do not backfill notifications.
2. Add a small owner-notification builder/enqueuer following the existing mail pattern, with a backend-only sender abstraction and Telegram implementation under Infrastructure. In `CommerceRepository.AcceptOnce`, enqueue only in the new-order branch before the existing commit, alongside email. Use accepted order snapshots and capture the configured owner chat in the protected payload, never the bot token. Enqueue failure rolls back acceptance; external delivery happens only after commit. Replay, refresh, tracking and recovered checkout cannot enqueue again.
3. Build plain-text messages containing order number/acceptance time, name, phone, email, complete delivery address, every purchased item/quantity/unit price/line total, subtotal/delivery/grand total in BDT, and customer notes. Label the acceptance event as awaiting manual confirmation/payment, not paid or owner-confirmed. Add the canonical `/admin/orders/{id}` staff link without credentials; delayed alerts direct the owner to current database state. Clearly delimit/indent customer-written fields and remove unsafe control characters without corrupting legitimate Unicode.
4. Handle Telegram's 4096-character text limit by splitting long orders into numbered parts, preferably at line boundaries. Reserve prefix space, keep each complete message below the limit, never split a surrogate pair, and include the same immutable order number plus part index/count in every part. Preserve all details rather than silently truncating 50-line orders. Persist progress after each successful part so retries resume at the first unacknowledged part.
5. Implement HTTPS JSON `POST https://api.telegram.org/bot{token}/sendMessage` with fixed host/method, configured numeric `chat_id`, `text`, and `link_preview_options.is_disabled=true`. Omit `parse_mode`/entities so customer text cannot inject HTML/Markdown, and do not enable paid broadcasts. Use the existing .NET HTTP facilities rather than adding a bot SDK. Require successful HTTP plus `ok=true` and a valid result/message ID; verify the returned recipient is the configured private chat. Apply bounded response reads, a 15-second request timeout and cancellation.
6. Register a separate background worker in `backend/src/ElectroApi.Api/Program.cs`. Claim rows with atomic conditional updates and a lease token; only the current lease may advance parts or finish work. Use a three-minute renewable lease and sequential sends spaced at least one second apart. Honor Telegram 429 `parameters.retry_after`, retry transient network/5xx failures with exponential backoff capped at one hour, and stop on permanent 400/401/403 errors. Limit each part to ten attempts and each pending payload to 24 hours; reset the per-part attempt counter only after acknowledged progress. Avoid competing HTTP-layer POST retries.
7. Make failures operationally safe: Telegram delivery never changes stock, order acceptance, fulfillment or payment. Log safe event/order identifiers and fixed failure codes, not raw request/response bodies, exceptions, customer PII or URLs. Scrub protected payloads on complete success, exhaustion or age-out, retaining non-PII progress/failure metadata. The owner reviews the existing protected staff order list and sanitized failure logs as the fallback; no new public notification/status/send endpoint is needed.
8. Replace customer-facing COD-exclusive headings/buttons/total labels, the COD-specific replay label and acknowledgment text in `frontend/src/components/checkout/checkout-form.tsx`. Retain explicit acknowledgment of the authoritative quote and all attempt/cart logic. Use "Place order" and "Order received. We will contact you to confirm the order and payment." Review `checkout/page.tsx`, `orders/order-receipt.tsx`, home/product/cart/footer copy, `lib/site.ts`, and acceptance-email subject/body for contradictory promises. Never mention Telegram or internal processing; keep actual fulfillment/payment badges truthful and the existing `Collected` guard unchanged.
9. Update the existing `README.md` during implementation with secure Telegram setup, API-only environment settings, retry/duplicate/retention limitations, and the staff-review fallback. ## Configuration And Setup

| API-only setting | Behavior |
| --- | --- |
| `OwnerNotifications__Enabled` | Explicit switch; checked-in default `false`. Disables real sending in local/CI runs. |
| `Telegram__BotToken` | Protected secret obtained through BotFather `/newbot`; validate bounded token syntax without printing it. |
| `Telegram__OwnerChatId` | Owner's numeric private-chat ID, parsed as positive signed 64-bit integer. No customer-controlled IDs, usernames or group/channel targets. |

- The owner uses a dedicated bot, sends `/start` privately, and obtains their own `message.chat.id` with a one-time authenticated `getUpdates` call. Confirm `chat.type=private` and the owner identity; never auto-bind the first stranger who messages the bot. Use the official API locally/server-side, not a third-party ID bot or token-bearing browser URL. No runtime inbound polling, webhook, bot command handler or public bot setup route is required.
- Store actual token/chat settings outside Git and build artifacts. Telegram embeds its token in the request path: suppress this client's HTTP URL logging and tracing/telemetry, sanitize failures, and test that the token cannot appear in captured logs. Do not paste real tokens into chat, README, browser history or CLI arguments.
- Validate enabled settings at startup without live network calls. Development may run with notifications disabled. In production, disabled notification configuration keeps new checkout paused through the existing generic maintenance behavior; configured outages after acceptance queue retries instead. Existing tracking/recovery, browsing and staff access remain available. Keep the existing independent `Commerce__CheckoutEnabled` deployment switch.
- Telegram bot chats are cloud chats, not end-to-end encrypted. Send only fulfillment/contact information to the owner's private chat, never application credentials, guest capabilities or generated payment secrets. Internal UX stays provider-neutral, but approved privacy/release review must still cover this data processing.

## Reliability And Rollout

- Guarantee one accepted order and one enqueued notification event, not exactly one external message. Telegram has no documented `sendMessage` idempotency key: a timeout or crash after sending but before progress persistence can duplicate the current part. Use bounded at-least-once attempts, stable order/part labels and database verification; never create another order to retry a notification. Acknowledged sending is not proof the owner read or confirmed it.
- Orders hold stock immediately and do not auto-expire. Failed/expired notifications leave the accepted order intact; staff must review/cancel pending orders through existing audited controls. Automatic cancellations, advance-payment accounting, notifications for later staff actions, resend dashboards, customer messenger alerts and inbound/delivery webhooks are out of scope.
- Pause checkout for the additive migration and paired API/frontend promotion, preserving existing deployment gates and rollback artifacts. Review migration SQL; do not reset/seed production or notify historical orders. Planning/implementation testing does not authorize deployment, production migration or live customer-data messages.
- Ordinary tests use a fake sender/HTTP handler. Before an explicitly authorized live rollout, the owner supplies protected configuration, completes BotFather/private-chat setup, confirms outbound HTTPS connectivity and verifies one sample order's full message parts. Reopen checkout only after existing post-deploy checks; provider failures must not be presented to customers.

Update copy-dependent existing Vitest/Playwright assertions without weakening behavioral checks.
